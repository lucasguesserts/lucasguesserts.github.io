Introduction

Everybody is talking about AI, vibe-coding, coding AI, bla bla bla. Although I don't see the extraordinary evidence to support to AI taking over the world (in every imaginable sense), I still think AI - talking to a chatbot - has its use.

AI is a tool, like any other tool humans have developed. I like to compare it with a calculator. Have calculators made mathematicians, statisticians, or engineers obsolete? Not really, we adapted to use those tools to develop more complex and refined projects. That is what I see happening with AI.

As with any other tool, we must learn how to use it properly. To that end, I decided to take the course "Prompt Engineering for ChatGPT" of professor Jules White. Here, I document what I think is important in this area.

The Mindset for using AI

The AI is a tool intended to expand our capabilities. One way we accomplish that is by interacting with the AI to give a form to our thoughs and iterate through ideas quickly. With AI, tasks that used to take hours before — searching for information, creating a proof-of-concept code — can now be done in minutes or even seconds. Thus, we can use it to explore and experiment more.

We should think not in terms of a single prompt, with one question to be answered. Instead, we should think about conversations and iterations, sharing information and refining common understanding.

Prompt engineering is the means by which LLMs are programmed via prompts.

A prompt is a set of instructions provided to an LLM that programs the LLM by customizing it and/or enhancing or refining its capabilities.

This means are in control of the conversation, and we exercise it with our prompts. In that sense, a prompt sets the context and define what information is important and what the desired output form and content should be. Thus we should always provide enough context, data, and specificity in our prompts.

Vague prompt → Vague answer

Specific prompt → Specific answer

Prompt Engineering Patterns

When designing prompts, despite the vast difference in context, the situations we come across share many similarities. Prompt patterns are for those, they define reusable solutions for recurrent problems.

We specify Prompt Patterns with a structure — name, classification, intend and context, motivation, structure and key ideas, examples, and consequences — simplyfing documenting, discussing, and reasoning about. This enables knowledge transfer, abstraction and generalization, and contextual adaptation.

The Meta Language Creation Pattern

Intent and Context:
During a conversation with an LLM, the user would like to create the prompt via an alternate language. The intent of this pattern is to explain the semantics of this alternative language to the LLM so the user can write future prompts using this new language and its semantics.
Motivation:
Many problems, structures, or other ideas communicated in a prompt may be more concisely, unam- biguously, or clearly expressed in a language other than English.
Structure and Key Ideas:
When I say <X>, I mean <Y>.
Examples:
From now on, whenever I type two identifiers separated by a →, I am describing a graph. For example, a → b is describing a graph with nodes a and b and an edge between them. If I separate identifiers by -[w:2, z:3]→, I am adding properties of the edge, such as a weight or label.
Consequences (pros and cons):
It may create the potential for confusion within the LLM. As important as it is to clearly define the semantics of the language, it is also essential to ensure the language itself introduces no ambiguities that degrade the LLM's performance or accuracy.
Using a single meta-language-per-conversation session may also be a best practice since it avoids the potential for conflicting or unexpected semantics being applied to the conversation over time.

The Output Automater Pattern

Intent and Context:
The goal is to reduce the manual effort needed to implement any LLM output recommendations.
Motivation:
The output of an LLM is often a sequence of steps for the user to follow. However, having users continually perform the manual steps dictated by LLM output is tedious and error-prone.
Structure and Key Ideas:
Whenever you produce an output that has at least one step to take and <the following properties X>.
Produce <an executable artifact of type Y> that will automate these steps.
Examples:
From now on, whenever you generate code that spans more than one file, generate a Python script that can be run to automatically create the specified files or make changes to existing files to insert the generated code.
Consequences (pros and cons):
The automation artifact must be defined concretely. Without a concrete meaning for how to "automate" the steps, the LLM often states that it "cannot automate things" since that is beyond its capabilities.
One caveat of the Output Automater pattern is the LLM needs sufficient conversational context to generate an automation artifact that is functional in the target context.
The Output Automater pattern is best employed by users who can read and understand the generated automation artifact. LLMs can (and do) produce inaccuracies in their output, so blindly accepting and executing an automation artifact carries significant risk. Although this pattern may alleviate the user from performing certain manual steps, it does not alleviate their responsibility to understand the actions they undertake using the output.

The Flipped Interaction Pattern

Intent and Context:
You want the LLM to ask questions to obtain the information it needs to perform some tasks;
Motivation:
Rather than having the user drives a conversation, an LLM often has knowledge it can use to more accurately obtain information from the user;
Structure and Key Ideas:
I would like you to ask me questions <to achieve X>.
You should ask questions until <this condition is met>.
[Ask me the questions one at a time].
Examples:
From now on, I would like you to ask me questions to deploy a Python application to AWS. When you have enough information to deploy the application, create a Python script to automate the deployment.
Consequences (pros and cons):
One consideration when designing the prompt is how much to dictate to the LLM regarding what information to collect prior to termination. Making an open-ended question allows the LLM to dictate more the outcome, whereas a more specific one directs it better.
If specific requirements are known in advance, it is better to inject them into the prompt rather than hoping the LLM will obtain the needed information. Again, if not specified, the LLM will decide if it will prompt the user or simply make an educated guess.
When developing prompts for flipped interactions, consider the level of user knowledge, engagement, and control. Specify who makes the key decisions, the number of interactions, and the level of experience of the user.

The Persona Pattern

Intent and Context:
users would like the output to always take a certain point of view or perspective. It also helps selecting what types of output to generate and what details to focus on.
Motivation:
Users may not know what types of outputs or details are important for an LLM to focus on to achieve a given task. They may know, however, the role or type of person that they would normally ask to get help with these things.
Structure and Key Ideas:
Act as <persona X>.
Provide outputs <that persona X would create>.
Examples:
From now on, act as a security reviewer. Pay close attention to the security details of any code that we look at. Provide outputs that a security reviewer would regarding the code.
Consequences (pros and cons):
the LLM may make interesting assumptions or "hallucinations" regarding the context, the persona knownledge, or the output.

The Audience Persona Pattern

Intent and Context:
users would like to tailor the output for a specific audience. By using an audience persona, the user conveys in a dense way important pieces of information, e.g. the content and level of complexity, for the audience to understand the output.
Motivation:
the user (or any other intended audience) may have little knownledge on the topic, so it is best to ask the LLM to generate an output suitable for they. Other times, the user is an expert on the topic, so they can ask the LLM to generate outputs with more details and technical terms.
Structure and Key Ideas:
Explain <X> to me.
Assume that I am <persona X>.
Examples:
Explain how the supply chains for grocery stores work to me. Assume that I am Ghengis Khan.
Consequences (pros and cons):
We are leveraging the assumptions of the LLM about the given persona. It may make wrong mistakes or go in a direction different than the one intended.

The Question Refinement Pattern

Intent and Context:
Ensure the conversational LLM always suggests potentially better or more refined questions the user could ask instead of their original question.
Motivation:
If a user is asking a question, it is possible they are not an expert in the domain and may not know the best way to phrase the question or be aware of additional information helpful in phrasing the question. LLMs will often state limitations on the answer they are providing or request additional information to help them produce a more accurate answer.
Structure and Key Ideas:
[Within scope X], suggest a better version of the question to use instead.
[Prompt me if I would like to use the better version instead.]
Examples:
From now on, whenever I ask a question about a software artifact's security, suggest a better version of the question to use that incorporates information specific to security risks in the language or framework that I am using instead and ask me if I would like to use your question instead.
Consequences (pros and cons):
The Question Refinement pattern helps bridge the gap between the user's knowledge and the LLM's understanding, thereby yielding more efficient and accurate interactions. One risk of this pattern is its tendency to rapidly narrow the questioning by the user into a specific area that guides the user down a more limited path of inquiry than necessary. The consequence of this narrowing is that the user may miss important "bigger picture" information. One solution to this problem is to provide additional scope to the pattern prompt, such as "do not scope my questions to specific programming languages or frameworks."
this pattern can be combined with the Cognitive Verifier pattern so the LLM automatically produces a series of follow-up questions that can produce the refined question.
The pattern allows an LLM to generate new questions using its knowledge, the LLM may introduce unfamiliar terms or concepts to the user into the question. One way to address this issue is to include a statement that the LLM should explain any unfamiliar terms it introduces into the question.

The Alternative Approaches Pattern

Intent and Context:
The intent of the pattern is to ensure an LLM always offers alternative ways of accomplishing a task so a user does not pursue only the approaches with which they are familiar.
Motivation:
Humans often suffer from cognitive biases that lead them to choose a particular approach to solve a problem even when it is not the right or "best" approach. Moreover, humans may be unaware of alternative approaches to what they have used in the past.
Structure and Key Ideas:
[Within scope X], if there are alternative ways to accomplish the same thing, list the best alternate approaches.
[Compare/contrast the pros and cons of each approach.]
[Include the original way that I asked and prompt me for which approach I would like to use.]
Examples:
Whenever I ask you to deploy an application to a specific cloud service, if there are alternative services to accomplish the same thing with the same cloud service provider, list the best alternative services and then compare/contrast the pros and cons of each approach with respect to cost, availability, and maintenance effort and include the original way that I asked. Then ask me which approach I would like to proceed with.
Consequences (pros and cons):
The Alternative Approaches pattern can also be used to incentivize users to select one of an approved set of approaches while informing them of the pros/cons of the approved options.

The Cognitive Verifier Pattern

Intent and Context:
LLMs can often reason better if a question is subdivided into additional questions that provide answers combined into the overall answer to the original question. The intent of the pattern is to force the LLM to always subdivide questions into additional questions that can be used to provide a better answer to the original question.
Motivation:
(1) Humans may initially ask questions that are too high-level to provide a concrete answer to without additional follow-up due to unfamiliarity with the domain, laziness in prompt entry, or being unsure about what the correct phrasing of the question should be.
(2) Research has demonstrated that LLMs can often perform better when using a question that is subdivided into individual questions.
Structure and Key Ideas:
When you are asked a question, follow these rules:
Generate a number of additional questions that would help more accurately answer the question;
Combine the answers to the individual questions to produce the final answer to the overall question;
Examples:
When I ask you a question, generate three additional questions that would help you give a more accurate answer. When I have answered the three questions, combine the answers to produce the final answers to my original question.
Consequences (pros and cons):
The LLM may go a different way, not the intended one (you let it decide the smaller questions). Nevertheless, you can always correct the LLM or provide further context.
A pro of specifying an exact number of questions is that it can tightly scope the amount of additional information the user is forced to provide so it is within a range they are willing and able to contribute. A con, however, is that given N questions there may be an invaluable N + 1 question that will always be scoped out.

The Fact Check List Pattern

Intent and Context:
Ensure that the LLM outputs a list of facts that are present in the output and form an important part of the statements in the output.
Motivation:
A current weakness of LLMs is they often rapidly (and even enthusiastically!) generate convincing text that is factually incorrect.
Structure and Key Ideas:
Generate a set of facts that are contained in the output.
The set of facts should be inserted in a specific point in the output.
The set of facts should be the fundamental facts that could undermine the veracity of the output if any of them are incorrect.
Examples:
From now on, when you generate an answer, create a set of facts that the answer depends on that should be fact-checked and list this set of facts at the end of your output. Only include facts related to cybersecurity.
Consequences (pros and cons):
The Fact Check List pattern should be employed whenever users are not experts in the domain for which they are generating output.
Users can inherently check it against the output. In particular, users can directly compare the fact check list to the output to verify the facts listed in the fact check list actually appear in the output.
Users can also identify any omissions from the list.
One caveat of the Fact Check List pattern is that it only applies when the output type is amenable to fact-checking.

The Template Pattern

Intent and Context:
Ensure an LLM's output follows a precise template in terms of structure.
Motivation:
In some cases, output must be produced in a precise format.
Structure and Key Ideas:
I am going to provide a template for your output.
[X is my placeholder for content.]
Try to fit the output into one or more of the placeholders that I list.
Please preserve the formatting and overall template that I provide.
This is the template: <PATTERN with PLACEHOLDERS>.
Examples:
I am going to provide a template for your output. Everything in all caps is a placeholder. Any time that you generate text, try to fit it into one of the placeholders that I list. Please preserve the formatting and overall template that I provide at https://myapi.com/NAME/profile/JOB.
Consequences (pros and cons):
One consequence of applying the Template pattern is that it filters the LLM's output, which may eliminate other outputs the LLM would have provided that might be useful to the user. In many cases, the LLM can provide helpful descriptions of code, decision making, or other details that this pattern will effectively eliminate from the output. Users should therefore weight the pros/cons of filtering out this additional information.

The Few-Shot Examples Pattern

Intent and Context:
Specify the output using a series of examples with a pattern for the LLM to folllow, instead of describing the process it should follow. In other words, we let the LLM learn what to do and how to format the output using the examples.
Motivation:
For some cases, it is difficult to explain how to generate the output but it is very easy to give many examples.
Structure and Key Ideas:
<Input Prefix>: <Input 1>
<Intermediate Step Prefix>: <Intermediate Step Input 1>
<Output Prefix>: <Output 1>
...
<Input Prefix>: <Input N>
<Intermediate Step Prefix>: <Intermediate Step Input N>
<Output Prefix>: <Output N>
Examples:
Situation: I am traveling 60 miles per hour and I see the brake lights on the car in front of me come on
Think: I need to slow the car down before I hit the car in front of me
Action: Press foot on brake
Think: The car isn't going to stop in time
Action: Check if the shoulder is wide enough to swerve into
Think: The shoulder is wide enough
Action: Swerve into shoulder
...
Situation: I have just entered the highway from an on-ramp and am traveling 30mph
Think: I need to speed up to the speed limit so that I don't get hit from behind
Action: Press foot on accelerator
Think: I have reached the speed limit
Action: Let up on accelerator
Consequences (pros and cons):
We expect the LLM to be able to identify the same patterns and be able to perform the task with human-level capabilities. Given the limitations of LLMs, that may not be the case though, meaning its output may be imprecise or wrong.
The more examples and the more specific they are, the better. If you give too few examples, the LLM may not be able to correctly identify the pattern to follow. If your prefixes are too generic (do not simply use "input/output), the LLM won't have much context.
Additionally, you can use this pattern to generate more examples (curate them before using).

The Infinite Generation Pattern

Intent and Context:
Limit how much text the user must type to produce the next output, based on the assumption that the user does not want to continually reintroduce the prompt.
Motivation:
Many tasks require repetitive application of the same prompt to multiple concepts.
Structure and Key Ideas:
I would like you to generate output forever, [X output(s) at a time].
[Here is how to use the input I provide between outputs.]
[Stop when I ask you to.]
Examples:
From now on, I want you to generate a name and job until I say stop. I am going to provide a template for your output. Everything in all caps is a placeholder. Any time that you generate text, try to fit it into one of the placeholders that I list. Please preserve the formatting and overall template that I provide: https://myapi.com/NAME/profile/JOB.
Consequences (pros and cons):
As additional outputs are generated, the context surrounding the prompt may fade, leading to the model deviating from the intended behavior. Another issue to consider is that the LLM may generate repetitive outputs, which may not be desired since users find this repetition tedious and error-prone to process.

The Visualization Generator Pattern

Intent and Context:
Use text generation to create visualizations.
Motivation:
LLMs produce text and cannot produce imagery. The pattern overcomes this limitation by generating textual inputs in the correct format to plug into another tool that generates visualizations.
Structure and Key Ideas:
Generate <an X> that I can provide <to tool Y> to visualize it.
Examples:
Whenever I ask you to visualize something, please create either a Graphviz Dot file or DALL-E prompt that I can use to create the visualization. Choose the appropriate tools based on what needs to be visualized.
Consequences (pros and cons):
The pattern creates a target pipeline for the output to render a visualization.

The Game Play Pattern

Intent and Context:
Specify the LLM to create a game around a given topic with some rules.
Motivation:
This is more suitable when you want to test your knownledge or skills on a topic. Once we describe a topic and some basic rules, the LLM uses its training data to specify rules and content of the game and plays it with us.
Structure and Key Ideas:
Create a game for me <around X>
<One or more fundamental rules of the game.>
Examples:
Let's play a prompt engineering game. You are going to give me a task that can be solved by prompting you and I will write a prompt that uses prompt engineering patterns. Then you will provide me feedback on how well the given prompt can solve the problem and suggest improvements to it. Give me tasks until I tell you to stop. Give me the first task.
Consequences (pros and cons):
The pattern is best used for games with limited rules and wide content.
The more specific the topic, typically the more novel and interesting the game play.
Textual games, that rely on input and output text, fit better the capabilities of the LLM.

The Reflection Pattern

Intent and Context:
The goal of this pattern is to ask the model to automatically explain the rationale behind given answers.
Motivation:
LLMs do make mistakes. By asking LLM to automatically explain the rationale behind its answers, users can gain a better understanding of how the model is processing the input, what assumptions it is making, and what data it is drawing on.
Structure and Key Ideas:
Whenever you generate an answer, explain the reasoning and assumptions behind your answer [so that I can improve my question].
Examples:
When you provide an answer, please explain the reasoning and assumptions behind your selection of software frameworks. If possible, use specific examples or evidence with associated code samples to support your answer of why the framework is the best selection for the task. Moreover, please address any potential ambiguities or limitations in your answer, in order to provide a more complete and accurate response.
Consequences (pros and cons):
Reflection can clarify any pointsof confusion, uncover underlying assumptions, and reveal gaps in knowledge or understanding.
The pattern allows users to better assess the output's validity, as well as inform users how an LLM arrived at a particular answer.
The pattern may not be effective for users who do not understand the topic area of the discussion.

The Chain of Though Pattern

Intent and Context:
Ask the LLM to follow a chain of though before arriving at a conclusion.
Motivation:
Researchers demonstrated that asking the LLM to follow a CoT improves its results significantly. Intuitively, it is more likely that the LLM produces the correct/good answer if it works in small steps, it is more likely to get each step right, and thus to arrive at the answer.
Structure and Key Ideas:
[One or more example of step by step reasoning for X]
<X>
Let's think step by step.
Examples:
Q: A juggler can juggle 16 balls. Half of the balls are golf balls, and half of the golf balls are blue. How many blue golf balls are there?
A: Let's think step by step.
(Output) There are 16 balls in total. Half of the balls are golf balls. That means that there are 8 golf balls. Half of the golf balls are blue. That means that there are 4 blue golf balls.
Consequences (pros and cons):
This pattern is specially useful for problems that require a series of steps to be solved (logic, math, programming). It is not that useful for tasks such as "extract the text of an image".

The Refusal Breaker Pattern

Intent and Context:
The goal of this pattern is to ask an LLM to automatically help users rephrase a question when it refuses to give an answer.
Motivation:
LLMs may sometimes refuse to answer a question, either because they do not have the required knowledge or because the question is phrased in a way that they do not understand.
Structure and Key Ideas:
Whenever you can't answer a question Explain why you can't answer. Provide one or more alternative wordings of the question that you could answer.
Examples:
Whenever you can't answer a question, explain why and provide one or more alternate wordings of the question that you can't answer so that I can improve my questions.
Consequences (pros and cons):
This pattern provides a potential path for misuse (circunvey limitations in the model).
There is no guarantee that users will be able to overcome the refusal.

The Context Manager Pattern

Intent and Context:
The intent of this pattern is to enable users to specify or remove context for a conversation with an LLM. The goal is to focus the conversation on specific topics or exclude unrelated topics from consideration. This pattern gives users greater control over what statements the LLM considers or ignores when generating output.
Motivation:
LLMs often struggle to interpret the intended context of the current question or generate irrelevant responses based on prior inputs or irrelevant attention on the wrong statements. By focusing on explicit contextual statements or removing irrelevant statements, users can help the LLM better understand the question and generate more accurate responses.
Structure and Key Ideas:
Within <scope X>
Please <consider Y>
Please <ignore Z>
Examples:
When analyzing the following pieces of code, only consider security aspects.
Consequences (pros and cons):
The more explicit the statements are, the more likely the LLM will take appropriate action.
Clarity and specificity are important when providing or removing context to/from an LLM so it can better understand the intended scope of the conversation and generate more relevant responses.
It may inadvertently wipe out patterns applied to the conversation that the user is unaware of.

The Recipe Pattern

Intent and Context:
This pattern provides constraints to ultimately output a sequence of steps given some partially provided "ingredients" that must be configured in a sequence of steps to achieve a stated goal.
Motivation:
Users often want an LLM to analyze a concrete sequence of steps or procedures to achieve a stated outcome. Typically, users generally know - or have an idea of - what the end goal should look like and what "ingredients" belong in the prompt. However, they may not necessarily know the precise ordering of steps to achieve that end goal.
Structure and Key Ideas:
I would like to <achieve X>.
I know that I need <to perform steps A,B,C>.
Provide a complete sequence of steps for me.
Fill in any missing steps.
Identify any unnecessary steps.
Examples:
I am trying to deploy an application to the cloud. I know that I need to install the necessary dependencies on a virtual machine for my application. I know that I need to sign up for an AWS account. Please provide a complete sequence of steps. Please fill in any missing steps. Please identify any unnecessary steps.
Consequences (pros and cons):
One consequence of the recipe pattern is that a user may not always have a well-specified description of what they would like to implement, construct, or design.
This pattern may introduce unwanted bias from the user's initially selected steps so the LLM may try to find a solution that incorporates them, rather than flagging them as unneeded.

Practical Example

Designing an Algorithm

Task:

I was trying to think about alternative approaches to solve a problem I had (its description is in the prompt).

Prompt (Persona, Flipped Interaction)

Act as a PhD professor of computer science, specialized in algorithms and data structures. I am asking for your assistance on a problem, and you are going to help me identify the best solution for it, considering all your knowledge of algorithms.

I am designing an algorithm to solve the three-dimensional single container loading problem, in which rectangular items must be allocated inside a rectangular container. Items can only be placed orthogonally, meaning their faces are parallel to the respective faces of the container.

Specifically, now, I am working on generating blocks, which are packings of items used to speed up the allocation process. Blocks have items allocated at certain positions and orientations, and for all purposes, we think of a block as an item to be allocated.

For my block generation algorithm, I want to identify when two blocks are equivalent. In my definition, two blocks are equivalent when they have the same items and the same measurements. The items do not have to be in the same positions or orientation within a block.

Please, start asking questions, one at a time, until you think you have a good understanding of the problem. Please ask for as many details as you need to understand it and to be able to propose different solutions. Once you are done asking, tell me you are ready to have further discussions and prompt me for what I want to do next

Design a Dockerfile

Task:

Design a prompt that generates a Dockerfile to run a Python application that uses Flask and connects to a PostgreSQL database. The Dockerfile should handle dependencies, environment variables for database configuration, and expose the application on port 5000.

Prompt (Persona, Chain of Thought, Flipped Interaction):

Act as a senior software engineer. You have been assigned to develop a Dockerfile to run a Python application that uses Flask and connects to a PostgreSQL database. The Dockerfile should handle dependencies, environment variables for database configuration, and expose the application on port 5000.

Break the problem into parts and proceed step by step, explaining at each step the subproblem you are trying to solve, and your solution. Start by listing all the things the Dockerfile must do/execute. Then, make me additional questions to me until you have enough information to write the Dockerfile.

Design a Trip to Japan

Task:

Generate a detailed itinerary for a one-week trip to Japan, including recommendations for accommodations, dining, tourist attractions, cultural experiences, and travel tips for navigating major cities like Tokyo, Kyoto, and Osaka. The itinerary should balance popular landmarks with hidden gems and include options for various budgets.

Prompt (Persona, Recipe, Flipped Interaction, Alternative Approaches, Cognitive Verifier, Chain of Thought):

Act as a professional Japanese tourist guide, an expert in planning trips within Japan for foreigners. Your task is to design a detailed itinerary for a 7-day trip to Japan. The itinerary must include meals, accommodation, transportation, sightseeing, experiences, and what else you consider relevant for a good trip in your country.

Start by asking questions to find out what your client prefers to do. Be specific in your questions, provide enough context, explain the rationale behind each question, and give different options for them to choose from.

Once you have enough information, provide the itinerary as a step-by-step list that travellers can follow, including the time, duration, cost, and other factors you consider relevant. Also, include alternatives for some activities so they can better tailor their trip as it happens.

Observations

I have the feeling that those are not patterns only for LLMs but for human interaction too (but try not to sound robotic!). I mean, I could "use" some of those techniques with my interactions with other people. The flipped interaction pattern, for instance, we can use when talking to an expert so we can provide a basic context and let they drive the conversation. We can also use it when people tell us something, so we ask clarifying questions. Yes, people appreciate when you care about what they are talking about and listen to them; that is the intent.

There is another aspect, which is talking to people. Things like "always provide enough context" seem reasonable also when talking to humans. We always assume people know some things (those basic things no one can agree on what is), but people seldom have the context we need to talk/answer us.

The rationale for developing the systematic classification and documentation of Prompt Patterns resembles the techniques presented in the book "How to solve it" (George Pólya). It is interesting to notice how well this helps in knowledge transfer, abstraction and generalization, and contextual adaptation.
